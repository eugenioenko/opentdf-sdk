The SDK's platform clients use the same authentication and transport as
encryption. Start with an authenticated `client` from the
[SDK example](../encrypt-and-decrypt/). Use an administrative identity for policy
changes; encryption permission alone does not grant administration access.

Examples run inside your application's function or async entry point. Go uses
your `ctx`, and C# uses your `cancellationToken`. Responses shown in the API
reference illustrate their shape; actual IDs and results come from your server.

## Browse requests and responses

Open a method in the [RPC reference](../../api/rpc/). Expand nested request and
response fields, inspect enum values, or follow a linked type. Each method has
native declarations in eight languages. JSON names, oneofs, presence, and
validation options come from the pinned platform's protobuf definitions.

Example JSON is checked against those message schemas during generation.
Server validation and authorization still apply when you make a request.

Replace the example UUID with the namespace ID returned by the platform.

## Look up an attribute by FQN

The JSON request uses a top-level `fqn`. It is part of the `identifier` oneof,
so do not also set `attributeId` or the deprecated `id` field. Native protobuf
libraries represent that oneof according to their language's conventions.

<UsageExample id="get-attribute-by-fqn" />

## Handle a missing attribute

Handle `not_found` separately and propagate other failures. An authentication
or permission error should not become a misleading "attribute does not exist"
result. Supply `attributeFqn` from your application; the C example uses a fixed
FQN and reports other failures to stderr.

<UsageExample id="handle-missing-attribute" />

See [errors and cleanup](../errors-and-lifetimes/) for cancellation and resource
ownership. The C service helpers return protobuf JSON; the other native clients
return typed protobuf messages.
